## 1. 复读：证据链

### 1.1 现场样本（数据库实锤）

会话 `sess_1790672838653_8809b3352a195962`（2026-09-29，`context_version=1`，即旧版患者路径）：

```
round 2 patient: 您就回一个『可以』，我没听明白——我是问治疗疼不疼，您能正面说说吗？
round 3 patient: 您就回一个『可以』،我没听明白——我是问治疗痛不痛，您能正面说说嗎؟
                  ↑ 中文逗号→阿拉伯逗号        ↑ 疼→痛      ↑ 吗→嗎   ↑ ？→؟
```

这句话不是模型“自己想说”的，它**逐字出现在旧版患者提示词里**（`backend/src/main.cpp:964`）：

> 示例（答非所问时）：客服上一轮只回「可以」。错误做法：回复「好的，那我大概明白了」……正确做法：回复「您就回一个『可以』，我没听明白——我是问治疗疼不疼，您能正面说说吗？」……

同一句提示词还在 `main.cpp:955` 明确要求：

> 你必须表达困惑或不满、**重复你的核心诉求或追问**……

所以 round 2 是**照抄提示词示例**；round 3 是采样器压住重复 token 后的**换皮复读**。

### 1.2 三个提示词污染源（v1 路径，29/33 场）

新会话里 **29 场是 `context_version=1`，只有 4 场走 v2（RAG 接地）**。也就是说，用户现在看到的绝大多数复读，来自旧版 `patientReply`，不是新 RAG 路径。

污染源 1：**逐字示例**  
`main.cpp:964` 的“正确做法”就是一句可直接复制的话。4B 模型在“客服只回一个词”的场景下会优先复用这句，因为它同时满足了“接住上一句 + 表达困惑 + 追问”。

污染源 2：**开场白被注入两遍**  
`patientReply` 把 `scenario["hidden"]` 整体 dump 进 system prompt（`main.cpp:974`），而场景的 `hidden_config` 里有：

```json
{
  "hidden": ["存在预算压力", "最担心手术疼痛"],
  "opening": "您好，我缺了一颗后牙，想问问种植牙大概怎么做，会不会很疼，要多久？",
  "instructions": "逐步透露对疼痛、预算、医生经验和复查安排的顾虑。若客服的回答答非所问、只有一两个词或没有回应你的疑问，不要当作已被回答：应表现犹豫或不满，重复你的核心疑问并追问……"
}
```

这段 `opening` 与 `history` 第 0 轮的患者开场白**完全一样**，等于同一句话在 prompt 里出现两次；4B 会把它当成“本场景的标准模板”来复读。主环境（`C:\Users\23732\CodeBuddy\20260912152152`）的代码注释里已经记录过同类故障：

> “scenario['hidden'] 里的 opening 与 history 第 0 轮的患者开场白是同一段文本……4B 模型直接把它当成‘本场景的标准模板’复读。”

污染源 3：**`instructions` 直接命令“重复”**  
上面 `hidden_config.instructions` 的原话就是“**重复你的核心疑问并追问**”。这不是模型自发行为，是场景作者写进去的行为指令。

> 这三条叠加，复读是“被教出来的”，不是模型随机故障。

### 1.3 为什么会出现简繁/标点变体

逐字复读之后，如果服务端/请求端启用了 `repeat_penalty` 或 DRY 采样，完全相同的 token 会被压低概率；4B 模型于是用**近义词、繁体字、异体标点**绕过惩罚：

- `疼不疼` → `痛不痛`
- `吗` → `嗎`
- `，` → `،`（阿拉伯逗号）
- `？` → `؟`（阿拉伯问号）

主环境的复读守卫代码把这类情况称为“换皮复读”，并专门做了 CJK 归一化 + 标点序列指纹：

> “把简体换成繁体，都算重复。”  
> “繁简转换不改标点、不改长度、不改句首，因此该判据在字形变化下依然成立。”

**结论**：逐字复读来自提示词；简繁/标点变体来自“反重复采样 + 没有 CJK 归一化检测”。两层都要修，单靠把 `repeat-penalty` 调高会加重变体。

> **一个必须指出的观测缺口**：目前无法从日志确认 10-13 的实例到底用了哪组采样参数。`tools/start-base.bat` / `start-demo.bat` 不传任何采样参数；`merge29-local/start-backend.ps1` 又提示用主环境的 `start-llama.ps1 -Action all`（它会传 `repeat_penalty 1.15 / DRY 0.8`）。llama-server 日志只记了 `n_ctx_slot`，没记 sampling；后端 `model_call` 审计也没记采样参数。这种“配了但不知道有没有生效”正是主环境注释里点名的历史坑。P0-6 的目的就是把采样参数变成请求体里的单一事实源，并写进日志。

## 2. 不说人话 / 记忆差

### 2.1 “不说人话”的三层原因

1. **模型能力**：4B + Q4_K_M，表达多样性和指令跟随天然有限。
2. **提示词过载**：`patientReply` 的 system prompt 有上千字，包含“硬规则”“示例”“禁止项”“JSON 结构”多层约束；4B 在长规则下容易退化成“安全但机械”的句式。
3. **温度过低**：患者 0.45、标准客服 0.2、RAG 客服 0.15（`main.cpp:986/1147/1294`）。温度越低越容易复读、越容易套模板。
4. **话术数据模板化**：训练语料里“理解您的顾虑”出现 **431—1155 行**（`multi_turn_train_merged.jsonl` / `multi_turn_train_v3.jsonl` / `clean_dataset_final.jsonl` / `oral_train_v3.json`），4B 很容易把它学成万能开场。
5. **固定兜底句**：`patient_grounding.h:125-132` 的 6 句固定回复、以及 `safe_prose` 不通过时的回退，会让听感更重复。

> 这不是“模型坏了”，是“4B 在超长规则 + 低温度 + 模板数据”下的典型退化。换 8B/云端会明显改善，但先把 prompt 缩短、温度抬到 0.5—0.7，收益也很大。

### 2.2 “记忆差”主要是错觉

- 现场 27 场已完成会话，**3—4 轮、全文 58—247 字**；基座 ctx 8192，prompt 最多 1—2k token，**没有任何上下文截断**。
- llama-server 日志里所有请求都是 `truncated = 0`；唯一一次 4096 溢出是 **微调槽** 收到 5633 token 的 RAG prompt（`sft-v4.err.log` 第 36 行），代码已经把 `groundedServiceReply` 固定到基座，属于已修复的历史问题。
- 用户感觉“忘了”，多数是因为患者**逐字重复上一轮**，看起来像没听见；以及 `hidden_config` 里同时有 `variants` 的多套顾虑，模型偶尔会跳到另一套设定。

**结论**：不要用“扩上下文/换大模型”来解决记忆问题；先解决复读和 prompt 污染。

**关键点**：  
- 失败**主要**发生在 `normalizeReport` / `evaluateTrainingJob` 的**逐字引用与轮次校验**，不是 JSON 解析失败；`d630163b` 的最后一次尝试才是连接超时。  
- 失败的会话只有 135 字符左右，**不是上下文溢出**。  
- v2 路径完成的 **2 场全部失败**（`d630163b`、`e87b4f7e`），说明新 RAG 评分链路还没有达到可上线状态。

### 3.2 代码层面的直接原因

`evaluateTrainingJob`（`main.cpp:2238-2242`）对每条 `strengths[].evidence` 做**严格子串匹配**：

```cpp
for (const auto& strength : communication.at("strengths")) {
  bool found = false;
  for (const auto& message : history)
    if (message["role"] == "user" && message["round"] == strength["round"])
      found = message["content"].get<std::string>().find(
          strength.at("evidence").get<std::string>()) != std::string::npos;
  if (!found) throw ApiError(503, "MODEL_INVALID_RESPONSE", "沟通优势必须引用客服原话");
}
```

`normalizeReport` 还要求：

- `strengths[].round` / `improvements[].round` 必须真实存在（`main.cpp:1956-1970`）；
- `violations[].originalQuote` 必须是对应轮次的逐字子串（`1980-1986`）；
- `roundComments` 必须覆盖每一轮、不能重复（`2009-2010`、`2083-2084`）。

4B 模型**能生成结构正确的 JSON，但做不到稳定逐字复制**。只要有一处 quote 是转述、少一个字、换一个标点，整份报告就被判废——这是“全有或全无”的校验策略，不是模型能力问题。

### 3.3 重试机制没有把错误告诉模型

`structuredCompletion` 的第二次尝试（`main.cpp:1459-1468`）只追加一句通用提示：

```
上一次生成未形成有效 JSON。本次必须只输出一个完整 JSON 对象……
```

它不知道“quote 不是逐字原句”或“round 不在白名单”，`evaluateCommunication` 也没有传具体 `repair_hint`。于是 3 次 job 重试都是**同一个 prompt、没有错误反馈**，每次都在同一个 quote 上失败——这是确定性失败，不是随机抖动。

更糟的是：第二次尝试把 `json_output` 关掉（`json_output = attempt == 0`，`main.cpp:1464`），温度降到 0，反而更容易输出散文。

### 3.4 两个“埋着”的隐患

**隐患 A：60 秒硬编码超时，`MODEL_TIMEOUT_MS` 是死配置**

`postLiteLlm`（`main.cpp:663`）写死：

```cpp
WinHttpSetTimeouts(session.get(), 10000, 10000, 10000, 60000);  // 读超时 60s
```

而 `merge29.env:43` 和文档都写着 `MODEL_TIMEOUT_MS=600000`（10 分钟）；全仓库 grep 不到任何读取 `MODEL_TIMEOUT_MS` 的代码。  
本次 18:57 的最后一次失败是 **2 秒内**连接失败（模型服务不可达/重启），不是 60s 生成超时；但一份 2800 token 的报告在 57 t/s 下约 49 秒，加上排队/冷启动，**60s 很容易被打穿**。这是潜伏的、会随报告变长而频繁出现的故障。

**隐患 B：截断后把输出预算翻到 8192，超过 8192 上下文**

`completionBudgetAfterTruncation`（`main.cpp:867-871`）：

```cpp
return current >= 4096 ? 8192 : std::max(6000, current * 2);
```

报告初始预算 4096，一旦 `finish_reason=length`，重试直接要 8192 输出；而基座 `-c` 就是 8192，prompt 还有 1—2k token：

```
prompt（1—2k） + 8192（输出预算） > 8192（上下文）→ llama-server 返回 400
```

代码把 400 映射成 `MODEL_ERROR`，不重试，job 直接失败。这个 bug 目前还没在 24 份报告里触发，但长报告一旦触发 `finish_reason=length`，就会走到这条死路。

## 4. 根因判定（模型 vs 调用）

| 现象 | 模型本身 | 调用/提示词/后端 | 判定 |
|---|---|---|---|
| 逐字复读 | 4B 指令跟随弱，倾向复用上下文 | v1 prompt 把 opening 注入两次、明确要求“重复你的核心疑问”、给出逐字示例；无代码去重 | **调用层为主** |
| 简繁/标点复读 | 受惩罚时选近义/异体 token | repeat_penalty/DRY 等反重复采样；无 CJK 归一化检测 | **采样+守卫为主** |

## 6. 换不换模型：决策矩阵

| 方案 | 质量提升 | 成本/风险 | 8GB 4060 可行性 | 建议 |
|---|---|---|---|---|
| **保留 4B，先修调用层** | 复读/报告失败可降一个数量级；“说人话”中等改善 | 1—2 天开发，0 硬件成本 | ✅ | **先做** |
| 本地 8B（Qwen3-8B / Qwen2.5-7B Q4） | 指令跟随、自然度明显更好；报告 quote 更准 | 5GB 权重 + KV，**不能和 sft-v4 同时常驻**；需卸载/串行加载，交互变慢 | ⚠️ 单模型可以，双模型不行 | 只有在“放弃 sft-v4 槽”或升级 16GB 后才考虑 |
| 云端 API（DeepSeek / Qwen） | 最大；报告/评分/患者都更稳 | 按 token 计费、网络依赖、数据出机 | ✅ 不占显存 | **若允许联网，优先用于报告/评分**；话术仍留 sft-v4 |
| 继续微调 4B / DPO | 话术风格可改善 | 数据/训练成本高，周期长 | ✅ | 不是当前瓶颈，暂缓 |

**推荐路线**：

```
是否必须完全离线、数据不出机？
├─ 是 → 保留 4B，做 P0；若仍不满意，升级 16GB GPU 或接受 8B 单模型（放弃 sft-v4）
└─ 否 → 报告/评分切云端（DeepSeek/Qwen），话术保留 sft-v4；
         用 30 场会话做 A/B（复读率、quote 通过率、报告成功率、人工偏好），再决定是否全量
```

**为什么不是“换个模型就好了”**：

- 报告失败的主因是后端 `find()` 校验，换 8B 只能降低概率，不能消除；云端模型也会转述。
- 复读的主因是提示词/场景数据；换模型后如果 prompt 不改，仍然会复读，只是措辞不同。
- 60s 超时、预算翻倍超 ctx、重试不带错误，这些换模型都修不了。
- 反过来，P0 做完后 4B 可能已经够用；这时再换模型，才能公平比较“模型上限”而不是“调用层 bug”。

> 换云端在代码上很轻：按现有“我的 → LiteLLM 模型配置”改 Base URL / 模型名 / Key 即可，不需要重写网关。但 **60s 超时、quote 校验、JSON 重试**如果不修，云模型一样会被打回。换句话说：**先把契约修好，再换模型，才能看出换模型到底带来了多少提升。**
