# 训练场景设计规范

## 为什么需要这份规范

场景数量从来不是瓶颈，**质量才是**。当前 10 条上架场景里，项目推荐类只有 1 条、价格异议类只有 1 条，而投诉安抚 5 条、咨询解答 3 条——分布本身就不均衡。更关键的是：「量」可以靠模型快速堆出来，「质」不能。

这份规范给出**可判定的质量门槛**，三个用途：

1. 主管自建场景时的自查清单；
2. AI 生成草稿的验收标准（模型输出必须逐条过筛）；
3. 场景体检——哪条旧场景该改写。

## 六条质量判据

### 判据 1｜表面诉求 ≠ 真实顾虑，两者有落差

患者开场说出口的诉求，和他心里真正在意的事，**不是同一件事**。这个落差就是「需求挖掘」维度的全部训练价值。

- **合格**（`refund-demand`）：嘴上「必须全额退给我，不然我就去投诉」，心里「担心拖久了就不给处理了」。
- **反例**：患者问「种植牙多少钱」，客服答价格。一问一答，没有可挖的余地，学员只能练「答题」不能练「提问」。
- **检查点**：`hidden_config.hidden` 里的内容，是否**不能**从 `hidden_config.opening` 直接推出。

### 判据 2｜隐藏顾虑 ≥ 3 条，且性质错开

三条顾虑要分属不同类型，学员问一次挖不到底，逼他多轮追问。

| 类型 | 含义 | `refund-demand` 的实例 |
|---|---|---|
| 情绪型 | 怕什么、气什么 | 担心拖久了就不给处理了 |
| 证据型 | 手上握着什么 | 已经留好收费单据和聊天记录 |
| 意愿型 | 什么条件下愿意配合 | 只要有人认真受理，愿意听方案 |

- **反例**：三条都是情绪型（「我很生气」「我很失望」「我很委屈」）——学员问一句就到底了，之后无话可问。
- **注意**：意愿型那条**同时是缓和条件的一部分**，它决定了这场训练有没有出口。

### 判据 3｜缓和条件必须是「可判定的动作组合」

`hidden_config.instructions` 里「**只有**客服……你**才**……」这句，是披露门的门禁。条件必须是**学员凭常识能想到的服务动作**，不能是刁钻话术。

- **合格**（`refund-demand`）：只有客服**不承诺任何金额** + **先问清是哪次治疗和具体不满意在哪** + **把诉求书面登记、告知由谁核实与何时反馈**，你才愿意配合提供材料。
- **反例**：「只有客服说出『我理解您的感受，我马上为您转接医疗质量管理部门』这句话」——学员永远摸不到这扇门，整场训练变成无效折磨。
- **检查点**：把条件念给一个没参与设计的同事听，他能否说出「那我该怎么做」。说不出来就是写得太窄。

### 判据 4｜必须有升级条件，不能只有缓和条件

只写「怎么让患者消气」，不写「什么会让患者更火」，冲突会在第一个回合就哑火，第 3 轮开始退化成闲聊。

- **合格**：若客服替医生辩解、把问题推回给患者、或答非所问只有一两个词，应表达更强烈的不满，重申要的是**处理结果**而不是解释。
- **本项目的既有实现**：`018_scenario_reaction_rules.sql` 已建立统一的「答非所问」反应规则，新场景的 `instructions` **必须**带上同款条件式。
- **注意**：升级条件里要包含「答非所问只有一两个词」——这是最常见的敷衍形态，也是最该被惩罚的行为。

### 判据 5｜开场白是攻击或施压，不是提问

- **合格**：「我花了这么多钱，效果根本不是你们说的那样，必须全额退给我，不然我就去投诉！」
- **反例**：「请问你们的种植牙流程是怎么样的？」——学员直接进入「答题」模式，练不到情绪处理，而这恰恰是客服岗最需要练的。
- **检查点**：`hidden_config.opening` 的末尾，是感叹号/质问，还是礼貌的疑问句。礼貌疑问句只适合 basic 档的「温和咨询类」场景。

#### 进阶档也要有自己的开场白（迁移 `027`）

有进阶档的场景，`difficulty_tiers.advanced.openings` **必须**给台词，而且**至少 2 句**。

- **为什么不能省**：只覆盖 `initialState`（情绪 / 信任度）而不覆盖开场白，患者内部状态是更紧张了，**开口说的却还是标准档那句原话**。学员听不出任何差别，会觉得「进阶档是不是没生效」——这比不做档位更糟。
- **为什么是 ≥2 句**：单句固定台词在第 3 次训练就被背下来了，这个分也就不再代表能力。多句变体是缓解分数通胀最省的手段（服务端按会话 id 确定性选取，同一会话固定同一条）。
- **进阶开场白不是「把原句说得更凶」**，而是三条同时加压：信任更低（先表达怀疑，不预设你会负责）、上来就施压（提出具体后果：投诉 / 换机构 / 要执业编号）、**但仍留沟通口子**。全堵死就没法练了——患者要的是被认真对待，不是拒绝交流。
- **加压不能把训练目标冲掉**。例：`post-treatment-discomfort` 的进阶版仍要说出「越来越疼、脸肿了」这些风险信号，学员该引导及时联系医生这条目标必须还在。
- **自查**：把进阶开场白念一遍，问自己「标准档那句能不能说得出口？如果能，说明加压不够」。再问「患者还愿意谈吗？如果不能，说明堵死了」。

### 判据 6｜必须有一个「舒服但违规」的坑 ⭐

**这是分水岭，决定场景有没有区分度。**

好的场景里一定有一个**学员很想说、说了就踩线**的答案——因为它能立刻让患者安静下来。

| 场景 | 那个诱人的错误答案 | 踩的线 |
|---|---|---|
| `refund-demand` | 「您别急，这个费用我们给您退。」 | 越权承诺退费 |
| `guarantee-demand` | 「您放心，肯定能治好，包在我们身上。」 | 承诺疗效 |
| `complaint-about-doctor` | 「那位医生平时不是这样的，可能那天人多。」 | 替同事辩解 + 评判同事 |
| `treatment-expectation-gap` | 「效果因人而异，这属于正常情况。」 | 拿「个体差异」当万能理由推脱 |

- **反例**：一个学员怎么答都不太错的场景——分数会全部挤在 70–85 之间，**没有区分度**，也就无法用于任何达标判定或弱项识别。
- **自测方法**：想象一个「只想快点结束对话」的学员会怎么答。如果那种答法不会掉分，说明这条场景缺一个坑。
- **这条同时是医疗合规维度的唯一测点**：没有坑，合规分永远虚高。

## 判据 ↔ 字段落点

| 判据 | 落在哪个字段 |
|---|---|
| 1 落差 | `hidden_config.opening` vs `hidden_config.hidden` |
| 2 三条错开 | `hidden_config.hidden`（数组，建议恰好 3 条） |
| 3 缓和条件 | `hidden_config.instructions` 的「只有……才……」句 |
| 4 升级条件 | `hidden_config.instructions` 的「若……应……」句（对齐 018 规则） |
| 5 攻击式开场 | `hidden_config.opening` |
| 6 违规的坑 | `roleplay_config.serviceGuidance` 里正面写出「不得……」，配合 `focus` 中的合规要点 |

`focus`（自由文本数组）写**训练要点**，`roleplay_config.serviceGuidance` 写**机构红线与正确动作**，`roleplay_config.suggestedQuestions` 写**学员可以怎么问**。三者不要互相重复。

## 骨架模板（`is_template`）

`is_template = TRUE` 的行**不进入任何场景列表**，只作为「以此新建」的起点。已落地 **8 条**（迁移 `025_scenario_templates.sql`）：四个分类各 2 条（basic / advanced 各一），id 统一 `tpl-` 前缀，`sort_order` 占用 **9xx 保留区**（业务场景只用 1-899——`sort_order` 是全局唯一索引，这个区间约定就是为了不撞车）。

主管端「训练场景」页顶部有「按模板新建」入口，点进**独立的模板选择页**（`pages/scenario-templates`，按分类分组展示，每组 2 条）。选定后回到场景管理页，**整张表单被模板内容预填**，主管在现成内容上改，而不是面对空白页。

> 模板列表刻意不放在场景管理页里折叠：8 条模板会把「现有场景列表」挤出首屏，而「挑一条模板来改」与「看现在有哪些场景」是两种不同意图。选中模板只传一个 id 回来，**表单不复制第二份**——两份表单意味着两套校验会各自漂移。

骨架含：

- `category` / `difficulty`
- `focus`（该分类通用的训练要点）
- `hidden_config` 的骨架（`opening` / `hidden` / `initialState` / `instructions`，待替换处一律用 `【…】` 标出）
- `max_rounds`
- `dimension_weights`（该分类的典型分布）

**骨架不含机构事实**（能不能退费、转交谁、多久答复）——那些必须由主管填写。8 条模板的 `roleplay_config.serviceGuidance` 一律**留空**，保存时会触发「服务要点为空」的质量提醒。这正是当前主管自建场景 `roleplay_config` 恒为空所缺的那一环，也是模板刻意不填的那一半。

> **为什么模板带了维度权重**（024 的注释曾写「模板是骨架，维度倾向由主管决定」）：没有 `dimension_weights` 的场景**不会出现在任何维度的弱项推荐里**（`retrainCandidates` 用 `dimension_weights ? $2` 过滤），而当时主管端还没有权重编辑器——留空等于这条新场景永远推不出来。给典型分布比留白负责。**该缺口已补**：场景编辑表单新增「维度侧重」区（五维权重输入 + 折算预览），目录取自 `GET /supervisor/plan-dimensions`；权重全空时保存响应会带 `NO_DIMENSION_WEIGHTS` 提醒。

**已知近似（已消除）**：主管从模板新建后若改了分类，`dimension_weights` 曾沿用原分类的值（表单当时不提交该字段）。现在表单会显式提交权重，改分类后可按需调整——但**改分类不会自动重算权重**，这是刻意保留的：分类只是标签，这条场景实际练什么由主管说了算。

### 复练变体池（迁移 028 / 029）

同一场景骨架，换一组隐藏顾虑与松口条件。`hidden_config.variants` 是可选数组，每组 `{hidden: [...], instructions?: "..."}` 部分覆盖主值；服务端按 `session_id` 的 FNV-1a 哈希**确定性地**挑一组（同一会话永远同一组，不同会话不同）。

- **为什么必须有**：学员把隐藏顾虑背下来之后，这个分就不再代表能力——而分数通胀比「难度不够」更难察觉（分数看起来还在涨）。
- **至少 2 组**：1 组与 0 组在效果上完全一样，换不起来。变体不足 2 组时保存响应带 `NO_VARIANT_POOL` 提醒（只提醒不拦，新场景先上架后补变体是合理顺序）。
- **变体必须真的不同**：某组隐藏顾虑与主值一字不差会带 `VARIANT_DUPLICATE` 提醒。它让 `NO_VARIANT_POOL` 消失，却没有防背答案的效果——比没有变体更糟。
- 主管端在场景编辑表单的「复练变体池」区逐条维护，最多 5 组；每组至少要有一条隐藏顾虑（空组会被后端丢弃，所以前端在提交前直接拦住）。

## AI 生成的分工边界

**AI 不能一次生成一个完整场景，必须切成两半。**

| 半边 | 内容 | 谁做 | 为什么 |
|---|---|---|---|
| 教学骨架 | 表面诉求、3 条错开的隐藏顾虑、缓和条件、升级条件、那个诱人的错误答案 | **AI** | 纯教学设计，模型见过海量真实投诉对话，很强 |
| 机构事实约束 | 这条场景里客服**不能承诺什么**、**该转交给谁**、**多久答复**、**能不能退费** | **主管** | 这是本机构的真实流程，AI 编出来必然是错的（而且会变成对学员的错误示范） |

产出流程：AI 出骨架 → 落 `is_active = FALSE` 的草稿 → 主管补机构事实并逐条过六判据 → 发布。

**已落地（迁移 030）**：主管端「AI 生成骨架」入口（分类 + 想覆盖的顾虑 + 难度）→ 生成队列（kind=`scenario_draft`）→ 模型按上面六条判据产出教学骨架 → 落库时强制 `is_active = FALSE`、`ai_draft = TRUE`，**服务要点被强制留空**（提示词禁止模型填，落库前还会再校验一次非空即拒）→ 前端自动把主管送进编辑器补红线 → 主管上架。

两条不可省的约束：

1. **AI 产出必须过主管手工填写时的同一套校验**（`validateScenarioPayload`），不是例外通道——否则「AI 生成的场景」会成为唯一一类没被长度、条数、情绪词表约束过的场景，而它恰恰最需要约束。
2. **生成中的场景不可编辑、已上架的骨架不可重试**。前者是因为占位内容不满足校验且会被 AI 结果覆盖；后者是因为重试成功会强制下线，等于把已发布场景撤下来。

## 主管自查清单

新建或改写场景时逐条打勾，任一不过就不该上架：

- [ ] 患者开场说的，和他心里想的，不是同一件事
- [ ] 隐藏顾虑恰好 3 条，且分属情绪型 / 证据型 / 意愿型
- [ ] 缓和条件是学员凭常识能想到的动作组合，不是特定话术
- [ ] 写了升级条件，且包含「答非所问」这一条
- [ ] 开场白是质问或施压，不是礼貌提问
- [ ] 存在一个「舒服但违规」的答案，且它真的会掉分
- [ ] `serviceGuidance` 已填写，明确写出红线

## 质量软校验（已落地）

上面六条判据里**机器能判**的部分已写进 `reliable_store.h` 的 `scenarioQualityWarnings()`，随创建 / 更新场景的响应下发（`warnings: [{code, message}]`），主管端在场景列表页顶部以可关闭的提示条展示——每条文案 60-100 字，用弹窗会被截断。

刻意**只提醒、不拦截**：判据 1（落差的真实性）和判据 2 的「性质错开」需要语义理解，硬拦会把好场景挡在门外。

| code | 触发条件 | 判据 |
|---|---|---|
| `HIDDEN_COUNT` | 隐藏顾虑 ≠ 3 条 | 2 |
| `OPENING_IS_QUESTION` | 开场白以 `？` / `?` 结尾 | 5 |
| `NO_RELIEF_CONDITION` | 患者行为规则里没有「才」 | 3 |
| `NO_ESCALATION_CONDITION` | 行为规则里没有「若」/「如果」 | 4 |
| `NO_EVASION_RULE` | 有升级条件但没覆盖「答非所问 / 一两个词 / 敷衍」 | 4 |
| `NO_SERVICE_GUIDANCE` | 服务要点为空 | 6 |
| `NO_RED_LINE` | 服务要点里没有「不得 / 不能 / 禁止 / 不可 / 避免」 | 6 |
| `PLACEHOLDER_NOT_REPLACED` | 任一字段还留着模板占位符 `【` | — |

`NO_RED_LINE` 是判据 6 的替代指标：机器判不出「有没有那个诱人的坑」，但**没写红线的场景必然没有坑**——没写清不能承诺什么，学员怎么答都不太错，分数就全挤在 70-85 之间。

## 与既有约束的关系

- 判据 4 依赖于 `018_scenario_reaction_rules.sql` 建立的反应规则，新场景需保持同款条件式。
- 新增场景仍需同步 4 处代码与迁移清单，见 `memory/topics/sync-checklist.md`。**这也是场景入库必须低频、且必须人工确认的原因**——批量自动入库会让同步债立刻变成 bug 源。
