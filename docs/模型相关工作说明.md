## 3. 微调工作

### 3.1 迭代脉络

```
sft_v2 → sft_v3 → sft_v4 → sft_v5
  ↑        ↑        ↑        ↑
 逐步迭代超参与数据；v4 为当前上线版本，v5 为对照/后续版本
```

### 3.2 产物形态

```
训练（AutoDL / LoRA）
      ↓
adapter_model.safetensors（126 MB）
      ↓
合并基座 + 量化
      ↓
sft_v4-Q4_K_M.gguf（2.33 GB）→ 8002 端口加载
```

### 3.3 分工依据（为什么微调只给表达类任务）

> 运行手册原文：**微调版（sft-v4）学的是"业务话术"，适合表达类任务；基座版（qwen3-4b-base）上下文更大（8192 vs 4096），适合理解与推理类任务。**

因此：**推理、评分、判定一律走基座；话术生成才走微调。**

### 4.3 采样参数（**当前问题的主要来源**）

| 参数 | 当前值 | 风险说明 |
|---|---|---|
| `--repeat-penalty` | 1.15 | 强度中等，压不住"近义改写"式重复 |
| `--repeat-last-n` | **256** | **只回看 256 token**；长输出后半段完全脱离惩罚窗口 |
| `--presence-penalty` | **未启用** | 无"是否出现过"的惩罚 |
| `--frequency-penalty` | **未启用** | 无"出现次数"累进惩罚 |
| `--dry-multiplier` | **未启用** | 无专门反循环采样器（llama.cpp 本版本已支持） |
| `--top-p` / `--min-p` | 0.9 / 0.05 | — |
| `-ctk` / `-ctv` | 默认 f16 | KV 未量化，扩上下文成本高 |

**代码侧**：`buildCompletionRequest` 只发送 `temperature` / `max_tokens` / `response_format`，**不发任何重复惩罚参数** —— 反循环压力全部依赖 server 端。

## 5. 各功能用哪个模型

**判定依据**：`structuredCompletion(..., use_tuned)` —— `use_tuned` 是**第 8 个**位置参数（`allow_plain_patient_reply` 是第 4 个，二者易混），默认 `false`。

| # | 功能 | 方法 | promptVersion | 槽位 |
|---|---|---|---|---|
| 1 | 患者初始化 | `initializePatient` | `patient-init-v2` | 主槽 |
| 2 | 患者回复（RAG 接地） | `groundedPatientReply` | `patient-reply-rag-v4` | 主槽 |
| 3 | 患者回复（旧路径） | `patientReply` | `patient-reply-v2` | 主槽 |
| 4 | 知识陈述提取 | `extractKnowledgeClaims` | `knowledge-extraction-v1` | 主槽 |
| 5 | 沟通四维评分 | `evaluateCommunication` | `score-rag-v1` | 主槽 |
| 6 | 五维评分（v1 路径） | `evaluate` | `score-prompt-v3` | 主槽 |
| 7 | 训练计划草稿 | `trainingPlanDraft` | — | 主槽 |
| 8 | **标准客服答复** | `standardServiceReply` | `service-reply-v3` | **微调** |
| 9 | **参考答案生成** | `idealServiceReplies` | `reference-answer-v1` | **微调（可配）** |
| 10 | 答案对比判定 | `compareAnswersAgainstReference` | `answer-comparison-v1` | 主槽 |
| 11 | RAG 接地客服答复 | `groundedServiceReply` | `service-reply-rag-v8` | **主槽（固定）** |
| 12 | 角色互换复盘 | `roleplaySummary` | `roleplay-summary-rag-v1` | 主槽 |
| 13 | 单轮复练点评 | `evaluateSingleRound` | `single-round-v1` | 主槽 |
| 14 | **实时训练提示** | `trainingHint` | `training-hint-v2` | **微调** |
| 15 | 知识/场景草稿 | `generateKnowledgeDraft` | `*-draft-v1` | 主槽 |

**结论**：15 个调用点中，**3 个走微调槽**（#8 / #9 / #14），**12 个走主槽**。

## 7. RAG 与嵌入模型

- **嵌入模型独立于生成模型**：换生成模型不需要换检索模型
- 使用 **query / document 两种任务前缀**，文档端前缀固定为 `document:title-body-applicability-v1`
- 向量缓存表 `knowledge_chunk_embeddings`，键 = `chunk_id` + `cache_key`（cache_key 含模型名、维度、提示词模板版本），文本变更才重算
- 检索阈值 `RAG_EMBEDDING_MIN_SIMILARITY = 0.65`
- 检索器版本串：`embeddinggemma-context-cosine-v4`

**RAG 覆盖的功能（6 项）**：患者初始化、AI 当患者回复、AI 当标准客服回复、知识准确性评分、错题单轮判定、管理端知识草稿预览。

**不覆盖**：参考答案对比评分（只用 scenario + history，不查知识库）。

## 8. 已知问题与诊断结论

### 8.1 复读（含简繁 / 标点替换）

**实测样本**（`2a195962`，同一会话第 2 轮 vs 第 3 轮）：

```
第2轮：您就回一个『可以』，我没听明白——我是问治疗疼不疼，您能正面说说吗？
第3轮：您就回一个『可以』،我没听明白——我是问治疗痛不痛，您能正面说说嗎؟
                    ↑                    ↑              ↑          ↑
              中文逗号→阿拉伯逗号    疼不疼→痛不痛      吗→嗎     ？→؟
```

**结论：这是"重复惩罚逃逸"，不是提示词诱导的复制。**

模型想重复同一句，但 `repeat-penalty` 压制了完全相同的 token，于是用近义改写 / 异体标点 / 繁体字绕过惩罚。如果是提示词让它照抄，会看到**逐字复制**，而不是系统性字符替换。

叠加因素：

1. `--repeat-last-n 256` 窗口过窄
2. 未启用 DRY / presence / frequency penalty
3. 温度接近贪心（评分 0.0、客服 0.15），贪心解码最易进循环
4. `response_format: json_object` 把模型约束在 JSON 字符串内，起循环后没有自然终止信号
5. Q4_K_M 量化压平低频 token 分布

**服务端缺口**：`patient_grounding.h` 只校验长度 ≤80、不含数字、不含违禁词，**不校验与上一轮是否重复**。

### 8.2 不说人话

| 原因 | 说明 |
|---|---|
| 客服回复温度 0.15 | 接近确定性输出，措辞僵硬 |
| 4B + 4bit 量化 | 表达多样性天然受限 |
| 规则回退 | `safe_prose` 不通过时回退到 6 句固定话术（`patient_grounding.h` 的 `replies` 表），听感重复 |
| 提示词模板化 | 大量示例句和高频短语，模型倾向复用 |

### 8.3 上下文记忆差

- 基座 8192、微调 4096；RAG 证据 + 多轮历史会显著挤占
- KV cache 仍是 f16，未量化，扩上下文成本高
- 微调槽 4096 已接近上限（`trainingHint` 的 prompt 实测 811～927 token，尚有余量但无冗余）

### 8.4 报告生成失败

**数据库实测**：24 场报告 `ready`，**3 场 `failed`**（任务 3 次尝试后 `dead`）：

| 时间 | 会话 | 错误码 | 判断 |
|---|---|---|---|
| 10-13 18:57 | `...99ce8026` | `MODEL_TIMEOUT` | **Windows HTTP 响应体截断**（该错误码同时承载"响应不完整/连接已中断"）|
| 10-13 18:30 | `...b396a457` | `MODEL_INVALID_RESPONSE` | 模型输出不满足契约（JSON 不可解析 / 字段或轮次不合规）|
| 09-29 17:15 | `...5cbb0cd6` | `MODEL_INVALID_RESPONSE` | 同上 |

**已排除**：上下文溢出 —— 三场失败会话的文本量分别只有 **135 / 1290 / 167 字符**。

**已定位的代码缺陷**：

```cpp
int completionBudgetAfterTruncation(int current) {
  return current >= 4096 ? 8192 : std::max(6000, current * 2);
}
```

报告生成初始预算 4096，一旦因 `finish_reason=length` 截断，重试直接要 **8192 输出 token**；而基座 `-c` 就是 8192：

```
prompt（数千 token） + 8192（输出预算） > 8192（上下文）→ 必然失败
```

该函数**既未考虑 prompt 实际占用，也未读取模型 n_ctx**。

### 8.5 证据边界

- 四个服务在 2026-10-13 已全部停止，无法现场复现
- `merge29-local\logs\backend.err.log` 只覆盖 10-13 11:23–12:35，**该时段 57 次模型调用全部 `finish=stop`、零重试、零错误** —— 不含问题时段
