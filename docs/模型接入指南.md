# 模型接入指南：如何用自己的模型跑这个小程序

> 面向：想把这个小程序接上**自己模型**的同事。
> 读完你能知道：系统分几层、模型在哪一层、它被要求做什么、以及换你的模型要改哪几处。

---

## 0. 先看这张图（30 秒理解整体）

```
┌─────────────┐   HTTP + JSON    ┌──────────────────┐   HTTP + JSON   ┌──────────────┐
│  微信小程序   │ ───────────────▶ │  后端服务（C++）  │ ───────────────▶ │  大模型服务   │
│ （界面/前端） │ ◀─────────────── │  （默认 8080 端口）│ ◀─────────────── │ （当前 DeepSeek）│
└─────────────┘                  └──────────────────┘                  └──────────────┘
```

- **第一层 小程序**：学员/主管看到的界面，负责发请求、展示结果。它不直接跟模型说话。
- **第二层 后端**：中转 + 把关。它既给小程序提供接口，也负责调用模型、并**严格检查模型返回的结果合不合格**。
- **第三层 模型**：真正"动脑子"的地方，负责生成患者台词、打分、给建议等。

**你（同事）要换的是第三层**——把当前的 DeepSeek 换成你自己的模型。前两层基本不用动，只需要改后端里"跟模型打交道"的那一小块代码。

---

## 1. 你需要先准备什么

| 项 | 说明 |
|---|---|
| 一个能提供模型的服务 | 最省事的是**兼容 OpenAI 接口格式**的模型服务（绝大多数主流模型、自建网关都支持），给一个能 POST 的地址即可 |
| 一个 API Key | 你模型的访问密钥 |
| 能改后端代码并重新编译 | 后端是 C++，用 Visual Studio 2022 编译（下文给具体改动点） |

> 如果你的模型**完全不兼容** OpenAI 格式（响应结构完全不同），也能接，只是要额外改一段"解析响应"的代码，第 6.4 节会讲。

---

## 2. 后端现在是怎么调模型的（现状）

模型相关的代码全部集中在 **`backend/src/main.cpp`** 一个文件里，拢共就这几处：

| 位置（函数） | 干什么 |
|---|---|
| `postDeepSeek()`（约 641 行） | 真正发 HTTP 请求的地方。**这里写死了模型地址** `api.deepseek.com` 和路径 `/chat/completions` |
| `buildCompletionRequest()`（约 834 行） | 拼请求体（发给模型的 JSON） |
| `structuredCompletion()`（约 1189 行） | 调模型 → 解析返回 → 失败自动重试 |
| `ModelGateway` 类（约 855 行起） | 9 个具体任务的提示词 + 输出处理 |

模型能力的"总接口"定义在 **`backend/src/model_gateway.h`**（`IModelGateway` 类），它列清楚了模型要会干的 9 件事。

### 2.1 请求格式（发给模型）

后端按 **OpenAI 兼容的 Chat Completions 格式**发请求：

```http
POST https://<模型地址>/chat/completions
Authorization: Bearer <你的 API Key>
Content-Type: application/json
```

```json
{
  "model": "deepseek-v4-flash",
  "messages": [
    {"role": "system", "content": "系统提示词（告诉模型它演谁）"},
    {"role": "user",   "content": "用户消息 / 场景信息"}
  ],
  "stream": false,
  "thinking": {"type": "disabled"},
  "temperature": 0.2,
  "max_tokens": 4096,
  "user_id": "demo-user",
  "response_format": {"type": "json_object"}
}
```

几个字段说明：

- `messages`：标准的多轮消息数组，`role` 取 `system` / `user` / `assistant`。
- `response_format: {"type":"json_object"}`：**强制模型只输出 JSON**。第一次请求会带，如果模型没返回有效 JSON，后端会自动去掉它、改成纯文本模式再重试一次（并在提示词里追加"只输出 JSON"）。
- `thinking`：这是 **DeepSeek 独有**的字段（关掉它的思维链）。你的模型若不带，要删掉（见 6.2）。
- `temperature` / `max_tokens`：每个任务不同，见第 4 节表格。

### 2.2 响应格式（模型返回）

后端按 OpenAI 兼容格式解析，它只认这几个字段：

```json
{
  "choices": [
    {
      "message": {
        "content": "模型真正输出的正文（必须是 JSON 字符串）",
        "reasoning_content": "（可选）思维链，DeepSeek 特有"
      },
      "finish_reason": "stop"
    }
  ],
  "usage": { "completion_tokens": 1234 }
}
```

- `choices[0].message.content`：**关键**，模型的输出正文。后端会从这里把 JSON 抠出来。
- `finish_reason`：`stop` 正常；`length` 表示被截断（后端会自动翻倍重试一次）；`content_filter` 表示触发内容安全。
- `reasoning_content`：可选，后端只用来记日志，不参与结果。

**好消息**：后端解析 JSON 时做了很强的容错——就算你的模型输出时多包了一层 Markdown 代码块（\`\`\`json ... \`\`\`）、带 BOM 头、或者前后夹了说明文字，后端都能把中间的 JSON 抠出来（见 `parseModelJsonContent()`，约 743 行）。

### 2.3 配置项（在哪填你的 Key）

后端从环境变量读配置（在 `backend.env` 或启动脚本里设）：

| 变量 | 作用 | 默认值 |
|---|---|---|
| `DEEPSEEK_API_KEY` | 模型密钥 | 空（不填会报"未配置密钥"） |
| `DEEPSEEK_MODEL` | 模型名 | `deepseek-v4-flash` |
| `DATABASE_URL` | 数据库连接 | 本机 PostgreSQL |
| `AUTH_MODE` | 登录方式 | `demo`（本机用）/ `wechat`（正式） |
| `PORT` | 后端端口 | `8080` |

> 注意：变量名叫 `DEEPSEEK_*` 是历史遗留，**换模型时可以直接复用这两个变量**，把模型名和 Key 填进去即可；嫌名字别扭可以改代码里的读取处（`main.cpp` 约 180 行）。

## 3. 模型要干的 9 件事（核心：这是换模型最容易踩的坑）

后端不是"让模型随便聊"，而是给模型**9 个具体任务**，每个任务都要求返回**特定结构的 JSON**。你的模型必须能稳定输出这些结构，否则后端会判"不合格"并报错。

| # | 任务 | 什么时候用 | 要求的输出 JSON |
|---|---|---|---|
| 1 | 虚拟患者 | 学员训练时，模型演"患者" | `reply` + 情绪/状态字段 |
| 2 | 评分器 | 训练结束，给整场对话打分 | 五维分数 + 逐轮点评 + 违规清单 |
| 3 | 标准客服 | 学员想看重播示范 | `reply` + 学习要点 + 合规边界 |
| 4 | 带依据客服 | 有知识库佐证时的示范 | `intro` + 引用的证据编号 + 要点 |
| 5 | 复盘助手 | 角色互换练习结束 | 总结 + 覆盖话题 + 原则 + 建议 |
| 6 | 单轮点评 | 错题"重练这一轮" | `passed` + 点评 + 建议话术 |
| 7 | 现场教练 | 训练中求提示 | `hint`（一条可照说的话术） |
| 8 | 计划草稿 | AI 帮主管出训练计划 | 标题 + 选哪些场景 + 达标线 |
| 9 | 场景骨架 | AI 生成训练场景的教学骨架 | 一套场景结构（见下） |

下面逐个给出**输出结构**（你调模型时拿这个去对）。

### 3.1 虚拟患者（`patientReply`）

```json
{
  "reply": "患者本轮的回复",
  "emotion": "平静|犹豫|焦虑|缓和|不满|愤怒",
  "emotionLevel": 0,
  "trustLevel": 50,
  "newlyRevealedInformation": ["本轮新透露的顾虑"],
  "riskTriggered": false,
  "shouldEnd": false
}
```

约束：`reply` 20—160 字；`emotion` 只能取那 6 个词之一；`emotionLevel` 是 -2 到 2 的整数（负=更不满/更紧张）；`trustLevel` 0—100；`newlyRevealedInformation` 最多 5 条。

### 3.2 评分器（`evaluate`）—— 最重要，校验最严

```json
{
  "dimensionScores": {
    "knowledgeAccuracy": 85,
    "medicalCompliance": 80,
    "empathy": 75,
    "needsDiscovery": 70,
    "serviceEtiquette": 88
  },
  "summary": "整体总结",
  "strengths": [{"round": 1, "evidence": "学员原话", "content": "做得好的点"}],
  "improvements": [{"round": 2, "content": "可改进的点"}],
  "violations": [
    {"round": 3, "originalQuote": "学员违规原话", "type": "类型", "reason": "为什么违规", "deduction": 10, "recommendedRewrite": "建议这样说"}
  ],
  "roundComments": [
    {"round": 1, "userMessage": "学员原话", "comment": "点评", "recommendedRewrite": "建议这样说"}
  ]
}
```

**死规矩（模型必须做到，否则整份报告作废）：**
- 五个维度分数必须是 **0—100 的整数**，不能是小数、百分数、0—1 的比值。
- 五个维度键名必须**一字不差**、一个都不能少、不能嵌套。
- 不能把五个维度全填 0。
- `roundComments` 必须**逐轮覆盖每一轮**学员发言，不能漏轮、不能引不存在的轮次。
- `violations` 没有违规就填空数组 `[]`。
- 医疗合规分要和违规扣分对得上（累计扣分 ≥30 时 `medicalCompliance` 不能高于 60）。

### 3.3 标准客服（`standardServiceReply`）

```json
{"reply": "标准客服答复", "learningPoints": ["要点1", "要点2"], "complianceBoundary": "本轮合规边界", "shouldEnd": false}
```

### 3.4 带依据客服（`groundedServiceReply`）

```json
{"intro": "不含数字和事实的回应", "evidenceIds": ["E1"], "learningPoints": ["要点"], "complianceBoundary": "...", "shouldEnd": false}
```

### 3.5 复盘助手（`roleplaySummary`）

```json
{"summary": "整体总结", "coveredTopics": ["已覆盖问题"], "keyPrinciples": ["关键原则"], "nextPracticeSuggestions": ["后续建议"]}
```

### 3.6 单轮点评（`evaluateSingleRound`）

```json
{"passed": true, "comment": "60字以内点评", "recommendedRewrite": "可直接照说的完整话术"}
```

### 3.7 现场教练（`trainingHint`）

```json
{"hint": "40—120字，含一句可直接对患者说出的完整话术"}
```

### 3.8 计划草稿（`trainingPlanDraft`）

```json
{"title": "计划标题", "description": "给学员的说明", "scenarioIds": ["场景id"], "requiredCount": 3, "requiredPassRate": 60, "dueInDays": 7, "rationale": "给主管的理由", "focusDimension": "empathy"}
```

约束：`scenarioIds` 只能从后端给的候选场景里挑（编造的会被直接丢弃）；`focusDimension` 只能取五个维度 key 之一，且必须是你所选场景真实覆盖的维度。

### 3.9 场景骨架（`generateKnowledgeDraft`）

这个任务用于 AI 生成训练场景的教学骨架（主管端「AI 生成骨架」入口）：

```json
{"name":"", "summary":"", "category":"", "hiddenConfig":{...}, "roleplayConfig":{...}, "dimensionWeights":{...}}
```

**注意这条路禁止模型写机构事实**（价格、退费、转交对象等一律留空，由主管填）。

> 完整字段结构以 `main.cpp` 里 `generateKnowledgeDraft()`（约 1131 行）的 `schema` 变量为准，上面是概要。
> 注：该任务此前还支持「服务草稿」「知识草稿」两种，它们对应的管理接口已移除，现在只保留「场景骨架」这一种。

## 4. 后端对模型输出有"双保险"检查

除了让模型输出 JSON，后端还会**再校验一遍**，不合格就判失败并重试（实在不行才报错）。你换模型时要留意这几条硬闸：

| 检查 | 后果 |
|---|---|
| 返回的不是合法 JSON | 自动重试一次（改成纯文本模式 + 追加"只输出 JSON"提示）；再失败则报错 |
| 患者回复的 `emotion` 不在 6 个词里 | 回退成当前状态，不写脏数据 |
| `emotionLevel` / `trustLevel` 越界 | 强制夹回合法区间（-2..2 / 0..100） |
| 评分五维全 0、或写成小数/百分数 | 判"评分无效"，触发重试 |
| 计划草稿里编造了不存在的场景 id | 直接丢弃那条，宁可选得少 |

## 5. 换成你自己的模型：改这几处就够了

按顺序做，改完重新编译即可。

### 5.1 改模型服务地址（必改）

`backend/src/main.cpp` 的 `postDeepSeek()`（约 641 行）里，把写死的地址换成你的：

```cpp
// 改这一行：把 "api.deepseek.com" 换成你的模型服务域名/IP
InternetHandle connection(WinHttpConnect(session.get(), L"api.deepseek.com", INTERNET_DEFAULT_HTTPS_PORT, 0));

// 如果路径不是 /chat/completions，改这一行：
InternetHandle request(WinHttpOpenRequest(connection.get(), L"POST", L"/chat/completions", ...));
```

### 5.2 改请求体（去掉 DeepSeek 特有字段）

`buildCompletionRequest()`（约 834 行）里，删掉你的模型不认识的字段。最典型的是 `thinking`（DeepSeek 独有）：

```cpp
json request = {
    {"model", model},
    {"messages", messages},
    {"stream", false},
    // {"thinking", {{"type", "disabled"}}},   // ← 你的模型不支持就删掉这行
    {"temperature", temperature},
    {"max_tokens", max_tokens},
    {"user_id", kDemoUserId},                 // 你的模型若不认 user_id 也删掉
};
```

`response_format: {"type":"json_object"}` 保留——绝大多数 OpenAI 兼容模型都支持，它能让模型稳定输出 JSON。如果你的模型不支持这个字段，删掉它，同时把提示词里"只输出 JSON"的要求再强调一遍（后端已有容错解析兜底）。

### 5.3 改配置项（Key 和模型名）

在 `backend.env` 里把 Key 和模型名填上：

```
DEEPSEEK_API_KEY=你的密钥
DEEPSEEK_MODEL=你的模型名
```

变量名可复用，不改代码就能跑；想改个贴切的名字，就改 `main.cpp` 约 180 行的两处读取。

### 5.4 如果你的模型不是 OpenAI 兼容协议（额外一步）

如果模型返回的结构和 OpenAI 的 `choices[0].message.content` 完全不同（比如返回 `{"result": "..."}`），改 `structuredCompletion()`（约 1189 行）里**解析响应**的那几行，把 `payload["choices"][0]["message"]["content"]` 换成你模型实际的字段路径即可。**其他地方不用动**——因为所有任务的提示词和输出校验都是围绕"content 里那个 JSON"做的，只要把 content 取出来，后面全复用。

## 6. 小程序前端怎么连到后端（一般不用动）

前端连后端，和模型无关。它读的是 `utils/config.js`：

```js
const API_BASE_URLS = {
  develop: 'http://127.0.0.1:8080/api',   // 本机开发
  trial: '',                              // 体验版（要填 HTTPS 地址）
  release: ''                             // 正式版（要填 HTTPS 地址）
};
```

- **本机开发**：默认已填好 `http://127.0.0.1:8080/api`，后端启动在 8080 就能连。
- **体验版/正式版**：必须填 HTTPS 地址，或在微信后台的扩展配置里设 `apiBaseUrl`。

**结论**：同事换模型，通常**只动后端**，前端一行不用改。

## 7. 接好之后，怎么验证真的通了

1. **启动后端**：双击 `backend/start-backend.cmd`（它会自动用最新编译产物）。看日志里有没有"模型密钥"相关的报错。
2. **看健康检查**：浏览器开 `http://127.0.0.1:8080/health`，返回里 `modelConfigured` 应为 `true`（表示读到了 Key）。
3. **跑一次真训练**：在小程序开发者工具里登录（demo 模式）→ 选一个场景开练 → 走完一轮，患者能正常回话就说明"虚拟患者"这个任务通了。
4. **看评分**：把训练走完，能出报告、有五维分数，说明"评分器"通了（这是 9 个任务里最严的一个，它通了别的基本都通）。
5. **看日志**：后端日志里会出现 `model completion attempt=1 mode=json finish=stop ...` 这类行，`finish=stop` 说明模型正常返回；出现 `attempt=2` 说明第一次 JSON 没生成对、走了重试（偶尔一次正常，频繁就要查提示词了）。

## 8. 常见坑（提前打个预防针）

| 现象 | 原因 | 处理 |
|---|---|---|
| 一直报"未配置模型密钥" | `DEEPSEEK_API_KEY` 没填或没被读到 | 检查 `backend.env`、启动脚本 |
| 报"模型服务暂时不可用" | 地址/路径不对，或服务没起 | 查 5.1 改的地址、看日志里的 HTTP 状态 |
| 日志里 `finish=length` | 输出被 `max_tokens` 截断 | 后端会自动翻倍重试；还不行就把对应任务的 `max_tokens` 调大 |
| 日志里频繁 `attempt=2` 且最终报"未返回可解析 JSON" | 你的模型不认 `response_format` 或输出格式不对 | 按 5.2 删 `response_format`，或 5.4 改解析 |
| 评分报告总判"评分无效" | 模型把分数写成小数/百分数/0-1 比值，或五维没写全 | 回看 3.2 的"死规矩"，把提示词里的量纲要求再强调 |
