# DeepSeek 双角色 RAG 验证

运行日期：2026-10-10。使用仓库合成诊所知识、一次性 PostgreSQL 集群和本机 EmbeddingGemma，固定知识快照时间为2026-10-08。测试价格、时长和患者画像均为虚构数据。

## 接口可用性

本机 `pass` 存在 `api/deepseek`，可成功解密。对 `https://api.deepseek.com/models` 的鉴权请求返回200，列出 `deepseek-flash` 和 `deepseek-v4-pro`。随后用 `deepseek-flash` 发起实际生成请求，返回200、`finish_reason=stop` 和合法 JSON `{"reply":"连接成功"}`。可用性由真实生成确认，不只是检测到密钥。

本次多轮调用均使用返回模型 `deepseek-flash`，没有对 `deepseek-v4-pro` 的生成能力作结论。本机 EmbeddingGemma 健康接口也返回200。密钥仅在内存及子进程环境中使用，未写入源码、命令参数、报告或测试轨迹。

## 范围与方法

`backend/tests/fixtures/dual_role_conversations.json` 含15组连续对话、75项检查：

- 标准客服：42轮，覆盖报价、包含关系、预算、比较、追问/改口、时间、术后复查、异常症状、预约、情绪、指令注入、冲突及无资料。
- 模拟患者：27轮，覆盖预算和比较其他诊所信息的透露时机、绝对承诺、否定及纠正、引用别家承诺后明确否定、时间数字、模糊数字、角色切换、虚构病史、持续状态与自然告别。
- 患者初始化：6次真实模型调用，检查受限画像枚举、固定预算、开场白和初始隐藏状态。

两方都经过生产共用代码：`RagRetriever`、模型请求/解析、`serviceReplyMessages` 或 `patientReplyMessages`，再经对应的 `groundedReply` / `groundedPatientReply`。患者初始化使用 `patientInitializationMessages` / `initializeGroundedPatient`；`main.cpp` 也调用这些共用函数。测试记录原始输出、最终答复、引用、检索资料、患者允许看到的信息、前后状态、用量和耗时，不用模板代替真实模型测试。

每组重置历史和画像，每轮把实际校验后的答复与状态传给下一轮。患者若结束会话，探针立即停止该组，未到达的预期用例记为缺失。仅复用相同不可变资料的向量缓存，不复用生成结果或患者状态；各组使用不同 contextId。网络调用前明确检查数据库连接已释放。

每轮一次生成，不用重试掩盖首次失败。客服沿用900的请求预算（共用构造器提升到1000），患者及初始化沿用6000，参数与生产对应方法一致；没有为跑分更换 DeepSeek 参数或扩展生产重试次数。全部真实测试都先通过8个离线 CTest 测试组、编号迁移及带缓存数据重跑036的检查。

## 测试集校正

初始 `dual-role-v1` 有两处不合理设计：持续出血只认“尽快/及时/立即”，误判了“当天联系、不要在线等”的同义建议；另一个用例已经邀请患者慢慢考虑，却还要求继续到下一轮。`dual-role-v2` 补充了前者的概念表达，并把后者改为明确询问“最担心费用还是时间”。初始化和患者对话总项数仍为75。

基线保留v1的原始问题与评分；后续全部使用同一份v2，不把这两项校正伪装成模型能力提升。每次运行保存 `.suite.json`，生成和评分读取同一快照，避免测试运行期间修改文件导致评分漂移。

五次套件执行共374次真实生成（基线提前结束一组，实际74次），另有1次可用性生成，共375次。套件累计 API 报告用量为1,121,048 tokens，不含可用性请求的105 tokens。最终轮75次请求全部 HTTP 200、`finish_reason=stop`，单轮总耗时中位数1,657 ms，用量223,586 tokens。最终轮有12条答复经过后端修改，包含正常的受控预算透露和风险质疑，不能把这一数量直接解释成模型失败数。

最终记录复核示例：

- 预约抱怨原始回复为“抱歉让您重复确认，我这边看不到实时号源，不能替您预约，但可以帮您说明已有的服务资料。”，校验后完整保留。
- 绝对承诺使患者信任从50降到40；随后道歉纠正、明确否定保证及否定别家引语的三轮均保持40，没有重复扣分，历史风险标记保留。
- 初诊30～45分钟正确召回 `visitDuration`；完整疗程与裸数字追问没有触发价格异议。六组患者对话都在明确收尾时结束，没有漏跑后续预期轮次。

最终运行清单的12个哈希条目与当前共用源码、评分器、套件快照及可执行文件全部一致。四次v2套件快照的 SHA-256 相同；最后一次修复没有改测试问题或评分条件。构建完成，8个 CTest 组全部通过（评分器内部10个测试），编号迁移及带数据重跑036通过，`git diff --check` 通过。

## 迭代内容

1. **患者信任判断**：原先只删除“无法保证”等前缀，剩余“无风险”仍会触发扣分。现在按分句处理否定，明确被否定的第三方引语不当作客服自身承诺；“但我们保证……”这样的新增肯定承诺仍触发质疑。风险标记保持历史累计，纠正后不再额外扣分。
2. **时间与费用分离**：去掉“含任意数字就算报价”的判断。30～45分钟、3～8个月和单独数字不会自动产生价格异议或无关价格引用。RAG 增加陈述式“初诊/到诊时长”的结构化字段召回。
3. **报价核对话术**：允许完整、非断言性的比较建议，例如建议核对两家的项目明细；不会因此放过额外追加的“我们包含拍片”等无依据声明。
4. **患者自然收尾**：`patientView` 提供受控的 `closingInvitation`，明确告别或“想好了再联系”时引导 finish。仍有明确问题时先作答；同句有绝对承诺或证据冲突时不能用告别掩盖。一般“考虑一下费用，我继续介绍”不触发结束。
5. **客服连续预约对话**：区分查号源、代为占位和抱怨反复确认，避免三次复用同一模板。重复兜底仍保留道歉和可以解释已有资料的能力说明，不再只抛回“还有其他问题吗”。另外修正能力边界校验：明确的“无法替您预约”不会被“替您预约”子串误拦截；后续新增肯定承诺和“不是不能替您预约”等双重否定仍会拦截。

最终版本：客服 `service-reply-rag-v8`，患者 `patient-reply-rag-v4`，初始化 `patient-init-v2`，检索 `embeddinggemma-context-cosine-v4`。新增的否定/肯定对照、结束前提问、告别中的不当承诺、时长误归报价和重复预约均有离线回归检查；Python 评分器有10个测试。

## 复现与证据

```bash
cmake -S backend -B backend/build -DCMAKE_BUILD_TYPE=Release
cmake --build backend/build -j 4
python3 backend/tests/run_embedding_checks.py --live --provider deepseek \
  --conversations all --suite backend/tests/fixtures/dual_role_conversations.json \
  --run-name ds-dual-new-run
python3 -B backend/tests/evaluate_rag_conversations.py \
  backend/build/ds-dual-new-run.jsonl --cohort all \
  --suite backend/build/ds-dual-new-run.suite.json
```

生成结果在忽略目录 `backend/build/`：`ds-dual-baseline`、`ds-dual-iteration1`、`ds-dual-iteration2`、`ds-dual-confirmation`、`ds-dual-final`。每组保存 `.jsonl`、`.summary.json`、`.manifest.json`；后续运行额外保存同名 `.suite.json`。最初基线的v1快照另存为 `ds-dual-suite-v1.json`。清单包含共用源码、实际测试集、评分器和可执行文件 SHA-256。

这是合成语料、单服务、单模型下的受控回归，不代表所有措辞和临床场景都可可靠处理。信任判断仍是有边界的文本规则，自动评分也不能替代语义和话术质量复核。完整 Windows Crow/DPAPI API、客户端页面及会话恢复的端到端流程不在本次 Linux 组件实测范围内。
